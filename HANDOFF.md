### November 12 (later): black screen diagnosed → VU1 path

- **Sema 18 is NOT a blocker.** `FUN_00293650` = `WaitSema(this+0x4c)` then sound/IOP shutdown, a ~100-tick delay and `DeleteSema`. `FUN_002936f0` (`+0x9c`) = `SignalSema`. So sema 18 is the **"quit game" signal**: `main()` starts the worker threads and blocks until shutdown. Thread 1 waiting there is correct. Earlier notes treating it as the root cause were wrong.
- User ran `--visible`: **black screen**. Frame dumps confirm both pages (FBP 0/80) are black apart from about 30 stray pixels at the top-left.
- **Loading is fine:** IOP opens `INDEX.IND`, `INDEX1.IND`, `DATA\SHADERS/TEXTURES/DATASETS/QUICKDAT/FLASHES.ARC` and reads them in healthy 2 KiB sectors. All I/O finishes in about 2 s, then the game sits in its per-frame loop.
- **GS sees:** ~17/s full-screen black clears (sprites) plus ~137/s bogus **POINT primitives at GS (0,0)** with random colours. GIF-channel (DMA ch2, chain mode) packets are legitimate texture uploads (`cnt`+`ref` chains). The bogus packets come from **VU1 XGKICK** (`ps2_vu1_core.cpp` `finishXgkick`): their payloads are raw floats (VU1 *input* data), not GIF packets. XGKICK sources include `0x5ee/0x78c/0x92a/0x9b4` qwords (VU1 data memory is 0x400 qwords) and the interpreter reports `[VU1 reserved lower] instruction=0xfffffffb` (its own "XGKICK packet overflowed buffer" sentinel) about 3,900 times in 12 s, at microprogram PCs `0xbf8`, `0xb98`, `0xba8`, `0x14b8`, `0x1170`.
- **Root cause is somewhere in VU1 microprogram emulation**: wrong integer/address math, wrong TOP/ITOP inputs, wrong UNPACK placement (V4-16/V4-32 with STCOL/mask), or a mis-emulated store. The VIF1 stream uses MPG uploads, BASE=0x3e/OFFSET=0xd3 double buffering, STCOL, UNPACK `0x6c`/`0x6d`, MSCAL, FLUSHA. VIF double-buffer logic in `ps2_vif1_interpreter.cpp` looks correct on review.

### November 12 (latest): XGKICK overflow fixed; VU1 packets still invalid

- New opt-in `SIMS_VU1_TRACE_DIR=<dir>` (+ `SIMS_VU1_TRACE_SKIP=<n>`). Records each VU1 microprogram run (pc, upper/lower words, vi1–vi15). At the (n+1)th oversized XGKICK it writes `vu1_trace.txt`, `vu1_code.bin` (16 KiB micro memory) and `vu1_data.bin` (16 KiB data memory).
- **First failing run:** the game's very first MSCAL is `0x122` → program **`0x910`** (TOP=0x3e). It is pipelined: `0b80 ILW.w vi3,0x30(vi0)` → `0b90 XGKICK vi3` (kicks the *previous* call's packet) → subroutine `0x6a8` stores this call's buffer into `0x30.w` (`06d0 ISW.w vi12,0x30(vi0)`). On the first call `0x30.w` = 0, so it kicks garbage. A simulated hardware GIF walk over that memory never reaches EOP either.
- **Fix:** PCSX2 `Gif_Unit::GetGSPacketSize` drops a PATH1 packet ≥ 0x4000 bytes (VU memory size) and carries on ("Bios does this"). PS2Recomp buffered 64 KiB and then `reportReservedInstruction(0xFFFFFFFB)` → `m_stopRequested`, **aborting the microprogram**. Now `VU1Interpreter::dropOversizedXgkick()` drops at the VU memory size, logs (capped/power-of-two), and VU1 keeps running. Test: "oversized PATH1 packet is dropped and the microprogram keeps running" (ps2x_tests 451/451).
- **Result:** the bogus POINT prims are gone, and the GS now gets only clean black clears (about 40/s instead of 17). But **every** kick is still dropped (8,192 in 30 s, from sources such as `0x50`, `0x228`, `0xda`), so the microprogram never builds a valid GIF packet in its output buffer.
- The 51st failing run (`SIMS_VU1_TRACE_SKIP=50`, scratchpad `vu1-2`) kicks `vi3=0x0d70` (wraps to 0x170). Qword 0x170 holds what looks like the program's constant table (z fields `0x3f,6,8,0x14,0x18,0x40,0x42,0x47,0x4a`), not a GIFtag. VI buffer pointers deliberately exceed 0x3FF (`0xd70`, `0xce6`) and rely on 10-bit wrapping. LQ/SQ/ILW/ISW/LQI/SQI/LQD/SQD all wrap consistently with `& (dataSize-1)`, so this is not a simple masking mismatch.
